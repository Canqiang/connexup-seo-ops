为「SEO Ops」设计 AM（Account Manager）工作台的界面原型，文件名 index.html，桌面 1280px 起，只使用设计系统 seo-ops 的 tokens.css 变量，不引入任何外部字体、图标或脚本库。整页是一份静态原型集：顶部一段说明，然后按下面顺序排 6 个区块，每个区块用 `<section id="…">` 包裹并带 h2 标题，所有状态并排静态展示，不依赖点击。

背景：这是内部 AM 用的操作系统。AM 同时服务多家餐厅商户，带领一个「人机混合团队」：AI Agent 负责诊断、关键词、内容、发布、报告，AM 自己也是团队成员之一，可以派单、接手、审核、人工执行。系统由 Plan（有限授权）和 Task（工作单）驱动，Orchestrator Agent 在授权范围内自动推进低风险工作，需要人决定的事进 AM 的收件箱。所有状态必须真实，不伪造进度。

全局导航（每个区块都画出来）：左侧固定竖栏，品牌块「SEO」，五个入口自上而下：工作台、商户、任务与计划、数据与报告、团队；当前页高亮。顶栏右侧「当前操作员 · xander · 退出」。

通用组件（沿用现有语言）：白卡片、1px 分割线、眉标（等宽小字大写）、戳记式状态、橙色主按钮、quiet 次按钮；提示条（error 红 / success 绿 / warning 橙）；确认对话框（眉标 + 标题 + × / 正文 / 取消 + 危险确认）。

6 个区块：

1）`am-home`：工作台首页。标题「工作台」，副标题「9 月 9 日 · 周三 · 你负责 5 家商户」。主区分四组，每组一个眉标标题和一行说明：
   a. 需要我决定（3 件 · 约 5 分钟）：三张决策卡。每张卡：左上商户戳记（如「George Merchant · 2020 Broadway」）、标题、三段小字「要做什么 / 为什么 / 你不处理会怎样」、右侧「产物预览」小块（如帖子正文前 80 字或 Plan 目标）、底部主操作（如「批准并发布」「批准 Plan」「批准预算」）和 quiet 次操作（「退回」「查看任务 ›」）。示例：
      - 「GBP 帖子草稿等你批准 · brunch 主题」，产物预览是帖子正文，操作「批准并发布」。
      - 「Q4 周期 Plan 待批准 · 7 项任务 · 无外部写入」，操作「批准 Plan」。
      - 「Local Falcon 扫描将消耗 40 credits」，操作「批准扫描」。
   b. 分派给我（2 件）：两张任务卡，戳记「HUMAN 执行」：「确认 Weekday Brunch Set 的价格与有效期（George）」截止今天 18:00；「向可可小卤索要官网后台权限」截止本周五。按钮「去处理」「转交给…」。
   c. 需要关注（2 件）：warning 提示风格：「可可小卤 · GSC 授权已过期，3 个任务被阻塞」；「Only Bear · 上一次发布结果未知，等待对账」。按钮「查看」。
   d. 仅知会（4 件，折叠列表，每行一句 + 商户 + 时间）：「Maya 已核对 3 家门店营业时间，无需修改」「关键词版本 v3 已激活」「周报草稿已生成，待你审核」「诊断 Run 完成，Plan 草稿 7 项」。
   右侧 rail：「团队」卡（成员列表：Orchestrator · 待命；内容 Agent · 工作中：正在准备 George 的帖子；审计 Agent · 待命；关键词 Agent · 待命；发布 Agent · 待命；xander（你）· 2 件待处理），每个成员一行：名字、角色、状态戳记（工作中 / 待命 / 阻塞）、一句当前在做什么。下面「今日节奏」小卡：已完成 11 · 进行中 4 · 等你 5 · 阻塞 3。

2）`am-merchant-space`：商户空间。面包屑「← 商户列表」，商户头部：名称「George Merchant」、门店「2020 Broadway · New York」、负责 AM「xander」、服务周期「2026-Q4 · 第 2 周」、里程碑「9 月：GBP 内容 4 篇 · 关键词监测集 20 词」、风险戳记「GSC 未授权」。五个 tab：概览（选中）、计划与任务、商户资料与记忆、数据与诊断、成果与报告。概览内容：左 2/3 是「当前 Plan」卡：目标「提升 brunch 相关本地可见度」、授权范围（允许：GBP 帖子发布（逐条审批）、只读同步、关键词重算；不允许：修改营业时间、付费扫描超过 100 credits）、有效期至 2026-12-31、进度条 7 项任务：3 完成 / 2 进行中 / 1 待审批 / 1 阻塞；右 1/3 是「本周节奏」和「未解决 blocker」两张小卡。下方「计划与任务」预览表：5 行任务，列：任务、类型、执行者（Agent 名或「xander」）、状态戳记、就绪性（READY / WAITING_INPUT / WAITING_AUTHORIZATION）、截止。

3）`am-task-detail`：Task 详情（AGENT 执行者版本）。头部：任务标题「为 2020 Broadway 发布一篇 brunch 主题帖子」、状态戳记「AWAITING_APPROVAL · 待审批」、来源「Plan #12」。主区自上而下四块：「做什么」（目标一句 + 参数表：门店、主题）、「为什么」（依据：Audit 发现 + 关键词簇 + 证据引用 3 条）、「当前成果」（帖子卡：图片占位、正文、CTA、门店；角标「AI 生成」）、「验收标准」（两条：读回正文与 CTA 完全一致且 LIVE；发布记录含 post_id）和「下一步」（主按钮「批准并发布」、次按钮「退回重新准备」）。侧区：负责人（内容 Agent · 准备阶段；发布 Agent · 发布阶段；你 · 审批），截止，前置任务 1 / 后置任务 0，批准状态「未批准」，成本「本任务已用 $0.42 · 2 次调用」，证据 3 条。底部「历史」：真实事件时间线 5 条（创建、派发、准备完成、等待审批…），每条有 actor 和时间；「技术 trace」折叠。

4）`am-task-detail-human`：同一 Task 详情，但执行者是 HUMAN（xander）且阶段是「人工执行」：标题「确认 Weekday Brunch Set 的价格与有效期」、状态「EXECUTING · 分派给你」。主区：「做什么」（向商户确认价格与有效期）、「为什么」（内容 Agent 不能把候选价格当经营事实）、「提交结果」表单：价格、有效期起止、来源备注、上传凭证（占位）、主按钮「提交确认结果」、次按钮「转交给…」「标记为无法完成」。侧区同上，负责人显示「xander（你）」，下面一行「阻塞了 1 个任务：GBP 帖子草稿」。

5）`am-dispatch-drawer`：对话派单抽屉，叠在商户空间上（右侧抽屉 480px 宽，左侧半透明遮罩）。抽屉头：「团队对话 · George Merchant」，下面一行范围戳记「范围：George Merchant · 2020 Broadway」。对话流四条：
   - 你：「下周推广早餐，不增加预算，内容先给我审核」
   - Orchestrator（戳记「提案」）：「已理解为：本周期内新增 1 篇 GBP 帖子任务，主题 brunch，发布前逐条审批，不新增预算。需要先确认 Weekday Brunch Set 的价格。」下面两张提案卡：「CREATE_TASK · GBP 帖子 · 内容 Agent」「REQUEST_HUMAN_INPUT · 确认价格 · xander」，每张卡右上戳记「待应用」，底部按钮「应用提案」「修改」。
   - 系统（灰色小字）：「提案已应用 · 2 个任务已创建 · 已派单」，戳记「已派单」。
   - Orchestrator：「内容 Agent 已开始准备不依赖价格的部分；价格确认后会自动补齐。」
   底部输入框「跟团队说点什么…」，@ 提示条：Orchestrator / 内容 Agent / 审计 Agent / 关键词 Agent / 交给我。

6）`am-team`：团队页。标题「团队」，说明「人和 AI 的职责、工作量与运行健康。active 只表示注册状态，不代表远端可用或本次已调用。」表格 7 行：成员、类型（HUMAN / AI_AGENT）、职责、允许的任务类型、当前工作量（进行中 n / 等待 n）、健康（戳记：正常 / 绑定漂移 / 未验证）、最近一次执行。成员：xander（HUMAN · AM）、Orchestrator、内容 Agent、审计 Agent、关键词 Agent、发布 Agent、报告 Agent（未启用）。右侧「能力目录」卡：列 3 个 Skill 及其引用状态（专用 / 共享，禁止覆盖）。

所有中文文案按上面原句使用。整体延续现有语言：瓷灰底、白卡片、墨蓝文字、橙色主按钮、戳记式状态，不要引入渐变、毛玻璃、大圆角或装饰性头像插画；成员用两字母首字母圆块代替头像。
