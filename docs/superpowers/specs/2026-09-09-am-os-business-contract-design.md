# AM OS 统一业务契约 v1：授权、任务、产物与异常

日期：2026-09-09
状态：待用户审阅
地位：`2026-09-09-agent-driven-local-seo-am-os-design.md`（目标架构）的细化与裁定记录；`2026-09-09-gbp-post-task-design.md`（第一个外部写闭环）遵守本文。三份文档冲突时，以本文为准，因为本文更具体、更晚。
来源：用户 2026-09-09 对 AM 工作台原型 v2 的审阅意见。原话要点：「方向已经基本一致，现在要优化的不是再加几个页面，而是让授权、任务、产物和异常处理形成一致的闭环」「安全不等于处处审批，Agent 驱动也不等于处处调用 LLM」。

## 0. 三条不变原则

后续所有页面、任务类型、Agent 配置都用这三条判断，不允许各页面各自定义规则。

| 编号 | 原则 | 判断方式 |
|---|---|---|
| P-A | **Agent 主动推进，AM 按职责参与。** AM 可以派单、沟通、提供事实、审核和执行，不是系统的人工调度器 | 任何让 AM「逐个点应用」「逐个确认低风险操作」的设计都违反本条 |
| P-B | **Plan 授权工作范围，内容审批授权具体产物。** 批准 Plan 不等于批准未来尚未生成的帖子 | Plan 只回答「允许做什么、花多少」；公开内容必须逐个产物批准 |
| P-C | **系统用证据判断完成。** Agent 说完成、接口返回成功、页面显示绿色，都不能替代交付核验 | 只有服务端核验证据能把任务推到 DONE |

## 1. 业务工作单与执行 Task

### 1.1 边界

- **Task** 是分派与交付的单位：有自己的身份、负责人、状态、产物、验收标准。
- **工作单**只负责聚合展示一组有先后关系的 Task（如 GBP 的草稿 → 审核 → 发布〔含远端核验〕），不持有独立状态。工作单进度由关联 Task 推导，禁止维护第二套状态。
- 不重新引入让用户管理的 Plan Version；Plan 变更走变更申请（§2），历史批准与引用保留。

### 1.2 每个 Task 必备

身份（id、类型、来源 Plan / 决策引用）、负责人（`assignee_type ∈ HUMAN|AGENT|SYSTEM` + id）、状态（现有状态词）、就绪性（派生）、产物（不可变、带 hash 与版本）、验收标准与核验策略、截止。

### 1.3 退回链

退回不改旧任务：审核 Task 以「已退回」完成并保留决定；系统创建新草稿 Task（`replaces_task_id` 指向旧草稿，退回理由进输入）和新审核 Task；旧产物只读保留。工作单显示版本链，默认折叠历史版本。

### 1.4 批准绑定五要素

一次内容批准精确绑定：正文（hash）、图片（sha256）、链接（CTA 类型 + 目标 URL）、门店（location_id）、发布时间（允许发布的时间窗 `publish_window`，以及有效期 `expires_at`）。五要素任一改变，批准失效（§3）。

### 1.5 工作单派生状态

| 关联 Task 状态 | 工作单显示 |
|---|---|
| 任一 Task NEEDS_ATTENTION | 需要处理（显示首要原因） |
| 否则，最靠后且非 PENDING 的 Task 所在步骤 | 该步骤的中文状态（草稿中 / 待审核 / 待发布 / 发布中 / 核对中） |
| 末位 Task DONE | 已上线（或该工作单类型的完成词） |
| 全部 Task 终态且含 CANCELLED | 已取消 |

### 1.6 展示

默认只展开当前需要处理的一步；历史、依据、技术 trace 按需展开。负责人、当前步骤、下一步说明只出现一次，不在流水线和侧栏重复。

## 2. 统一授权规则

### 2.1 决策表

同一套规则决定系统行为，Orchestrator 提案与界面按钮都是它的投影。

| 编号 | 情况 | 系统行为 | Orchestrator 命令 | 界面 |
|---|---|---|---|---|
| R1 | Plan 范围内，参与者权限与预算额度满足 | 自动创建、分派、推进 | `CREATE_TASK` / `ASSIGN_TASK` 直接应用 | 「已在 Plan #N 授权范围内创建并分派」，仅知会 |
| R2 | 缺商户事实或凭证 | 创建人工输入任务 | `REQUEST_HUMAN_INPUT` 直接应用 | 进「分派给我」，说明缺什么、阻塞了谁 |
| R3 | 需要审核具体公开内容 | 创建人工审核任务 | `CREATE_TASK`（审核类型）直接应用 | 进「需要我决定」，只给「审阅」入口 |
| R4 | 超出目标、资产范围或预算额度 | 提出变更申请，整组等待 | `PROPOSE_PLAN_CHANGE` / `REQUEST_APPROVAL` | 进「需要我决定」，整体批准或退回，不只创建前半段 |
| R5 | 发布结果未知 | 先核验，不能重发 | 无（服务端规则） | 核验中；核验失败进「需要我决定」，动作「开始核验」 |

### 2.2 判定输入

Plan 的授权范围必须结构化到能被程序判定：允许的操作类型（如 GBP 帖子发布〔逐条审批〕、只读同步、关键词重算）、资产范围（门店列表）、预算额度（按资源计：credits、美元；按次数计：本周期帖子条数）、有效期。参与者权限来自团队注册表；商户凭证状态来自同步记录。

### 2.3 付费操作

付费操作不一律重新审批：**已有明确额度授权就按规则执行，超出或没有授权才申请。** 例：Plan 允许「付费扫描不超过 100 credits」，一次 40 credits 的 Local Falcon 扫描按 R1 自动执行并在仅知会里记账；累计将超过 100 时按 R4 申请。原型 v2 首页让 AM 批准 40 credits 的扫描，违反本条，v3 修正。

### 2.4 「本次为什么需要你」

凡是进「需要我决定」或「分派给我」的事项，都必须说明触发的规则编号与事实：例如「R4 · Plan #12 付费扫描额度 100 credits，本周期已用 80，本次 40」。只显示一个审批按钮而不解释，视为缺陷。

## 3. 批准与失效

### 3.1 批准记录

`task_approvals`：审批对象（审核 Task、草稿 Task）、五要素 hash、商户 / 资产 / 操作范围、真实审批者（服务端登录身份，不接受模型转述）、决定（APPROVED / RETURNED）、有效期、撤销信息。审核完成与发布授权分开存证（AM OS §9.2）。

### 3.2 失效触发

| 触发 | 行为 |
|---|---|
| 产物任一要素改变（新图、改 CTA、改正文） | 批准 `INVALIDATED`；发布 Task 回到 WAITING_AUTHORIZATION；创建新审核 Task |
| 目标改变（门店、发布时间窗） | 同上 |
| 有效期到、发布时间窗过 | 批准 `EXPIRED`；发布 Task WAITING_AUTHORIZATION；通知负责 AM 决定重新审核或取消 |
| AM 撤销 | 批准 `REVOKED`；同上 |
| Plan 到期或变更申请生效后不再覆盖此操作 | 批准 `REVOKED`（原因 Plan）；工作单需要处理 |
| 审批者失去该商户权限 | 批准 `REVOKED`；创建新审核 Task 给新负责 AM |

### 3.3 发布必须停止

发布 Task 触发前重新校验批准有效且五要素未变；不一致则不发布。已经发出的单次外部调用无法中止，此时按 R5 处理，不因失效而重发或补发。

## 4. 异常恢复是主流程

### 4.1 四组状态

每组都要回答四个问题：谁处理、系统已经尝试什么、下一步是什么、什么时候升级。

| 组 | 触发 | 系统自动做 | 谁处理 | 下一步 | 升级 |
|---|---|---|---|---|---|
| E1 退回 → 修改 → 新审核 | 审核 Task 退回 | 建新草稿 Task（带退回理由）与新审核 Task；退回理由进候选经验 | 内容 Agent 重做；AM 再审 | 新草稿完成后 AM 收到「审阅草稿 v(N+1)」 | 同一工作单退回 ≥ 3 次 → 需要处理，建议 AM 补充事实或改主题 |
| E2 批准后产物变化 → 批准失效 | §3.2 任一触发 | 标记失效、发布 Task 停在 WAITING_AUTHORIZATION、建新审核 Task | AM 重新审核 | 审阅新版本 | 失效后 48 小时无人处理 → 需要处理 |
| E3 发布超时 → 自动核验 → 人工介入 | 发布 attempt 超时 / 无 post_id / 多次调用 | 直接进核验；按退避自动重读；绝不重发 | 服务端核验；用尽后 AM | 唯一匹配 LIVE → DONE；否则「开始核验 / 查看读回列表」 | 重读用尽即进「需要我决定」 |
| E4 输入任务取消 → 下游重新规划 | 人工输入任务被取消或转为受阻超期 | 下游任务 WAITING_DEPENDENCY；向 Orchestrator 发重新规划事件 | Orchestrator 提案：解除依赖（带理由）/ 替换输入来源 / 取消下游；范围外的走 R4 | AM 看到提案或自动应用结果 | 24 小时无提案 → 需要处理 |

### 4.2 影响范围分级

不是任何错误都暂停整家商户。默认只限制受影响的任务，按原因扩大：

| 级别 | 触发 | 范围 |
|---|---|---|
| 任务级（默认） | 单次准备失败、结构化输出不合格、读回不匹配、依赖缺失 | 只该任务 NEEDS_ATTENTION，其余照常推进 |
| 商户级 | 商户凭证失效（GSC / GBP 授权过期）、商户预算耗尽、商户 Plan 到期 | 该商户依赖该凭证或预算的任务全部受阻；不依赖的（如内部草稿）照常 |
| 项目级 | 提供方不可用（Core AI、FBR、Local Falcon）、Agent 绑定漂移 | 依赖该提供方的任务类型全部暂停，一条项目级提示，不逐商户重复 |

### 4.3 异常卡模板

标题（业务语言）· 影响（几个任务、哪家商户）· 系统已尝试（次数、最后一次时间、结果）· 现在需要谁做什么（一个主操作）· 何时升级。技术枚举与 trace 折叠。

### 4.4 两条禁令

不盲目重发（R5）；不盲目升级模型——缺事实、缺权限的失败换更强模型也解决不了（§7.2）。

## 5. 收件箱归类与优先级

### 5.1 单一归属

每个事项只出现在一组，按交付物类型判定，不按任务类型：

| 组 | 判定 | 例 |
|---|---|---|
| 需要我决定 | 我是负责人，交付物是一个决定，且决定会门控外部效果（发布、花费、Plan 变更）或核验责任 | 审阅草稿、整体批准变更申请、开始核验 |
| 分派给我 | 我是负责人，交付物是工作或输入 | 确认价格、索要权限、审阅周报草稿（导出与交付是另外的动作） |
| 需要关注 | 我不是执行者，但有明确责任人与动作的阻塞 | GSC 授权过期 · 责任人 xander · 动作 重新授权 |
| 仅知会 | 无需任何动作 | 已派单、已激活、已完成且无需修改 |

审核任务不同时出现在「需要我决定」和「分派给我」。

### 5.2 优先级

排序键：风险等级（外部写 > 花费 > 内部）→ 截止时间 → 被阻塞的下游任务数 → 创建时间。首页按此排序，不按商户分组。

### 5.3 密度

每张卡三行：结论、影响、当前有效操作；依据折叠；其他操作放次级入口。团队栏可收起。计数只数事项：「待处理 N 件」是事项数，「涉及 M 家商户」单独显示，两者不混算、不去重成一个数。

## 6. 记忆：服务改进，不成为第二套业务真相

### 6.1 三类内容

| 类 | 内容 | 权威来源 | 进入方式 |
|---|---|---|---|
| 经营事实 | 地址、营业时间、价格、供应时段 | SEO Ops 商户资料（商户确认 / GBP 快照 / AM 录入） | 只从资料表读，记忆不得覆盖 |
| 业务规则与偏好 | 品牌措辞、图片偏好、审批要求 | 商户风格档案与 Plan | AM 确认后生效，有作用范围与来源 |
| 候选经验 | 从退回、失败、效果总结的线索 | Core AI 原生记忆 + 退回理由 | 只作提示；未确认不进入发布前事实检查 |

### 6.2 使用条件

继续复用 Core AI 原生记忆，不另造经验引擎。**商户隔离是使用条件，不是黄色提示**：未证明按商户作用域隔离前，任何 Agent 调用都不注入记忆（`enable_memory=false`），页面显示「未启用 · 隔离未验证」。

### 6.3 确认 ≠ 有效

AM 确认「这个偏好适用」只把候选变成规则；「这个策略有效」（如「周三发帖效果更好」）是假设，需要后续数据验证，标记「待数据验证 · 验证周期 4 周」，验证前不推广到其他商户。

### 6.4 度量

重复错误是否减少、一次通过率是否提高、单条内容成本是否下降。记忆条目数不是指标。

## 7. 模型与成本

### 7.1 按工作阶段分配

| 阶段 | 档位 |
|---|---|
| 编排、复杂诊断、证据冲突 | 高能力模型 |
| 常规草稿、改写、格式整理 | 经济模型 |
| 同步、计算、权限检查、发布、核验 | 确定性程序（不调用 LLM） |

角色与模型不永久绑定；同一 Agent 在不同阶段可用不同档位。原型 v2 里「审计 Agent = 确定性程序」「报告 Agent 一直用高能力」的写法作废。

### 7.2 升级限制

升级条件必须是可判定的（如结构化输出连续 2 次不合格），每任务升级 ≤ 1 次、每商户每日升级次数与预算有上限。缺事实、缺权限导致的失败不允许升级，直接走 R2 / 需要处理。

### 7.3 成本三态

`已消耗`（已结算账单）、`已预留`（正在执行的任务按上限预留）、`未结算`（已完成但账单未回）。预算检查时点：任务触发前检查 已消耗 + 已预留 + 未结算 ≤ 额度；不依赖延迟账单限制正在执行的工作。

## 8. 看板、分析与交付报告

### 8.1 三层

| 层 | 用途 | 数据 | 产物 |
|---|---|---|---|
| 表现看板 | 查看最新数据；选择商户、门店、期间、比较期 | 最新同步 | 无文件 |
| 分析与 Audit | 解释问题、展示证据、交给 Orchestrator 提出计划 | 快照 + 证据引用 | Audit 报告、可转 Plan 任务 |
| 冻结报告 | 固定数据与结论，审核后形成正式交付物 | 冻结快照 | PDF / PPTX + 交付记录 |

### 8.2 覆盖清单

把旧报告（`2026-09-03-performance-dashboard-history-design.md` 与既有 HTML/JSON 报告）的信息逐项映射到三层中的页面或字段，形成覆盖清单；有 PDF/PPTX 按钮不等于覆盖完成。

### 8.3 草稿导出

内部草稿可以导出，文件与页面明确带「草稿 · 未审核」标识；正式交付版才要求通过审核。生成文件、下载、对客户发送是三个不同动作，各自留记录。

## 9. UI 减法清单（原型 v3 的输入）

保留导航、配色、工作单布局。集中调整：

1. 首页提高密度；按 §5.2 排序；每卡三行。
2. 审核任务只在「需要我决定」出现。
3. 工作单：负责人、当前步骤、下一步说明只出现一次；只突出当前有效操作。
4. 派单抽屉与决定卡显示「本次为什么需要你」（规则编号 + 事实）；40 credits 在 100 额度内自动执行。
5. 补四组异常状态（§4.1）的界面，每张异常卡按 §4.3 模板。
6. 记忆页按 §6 三类分栏；隔离未验证时显示「未启用」而非警告色。
7. 模型与成本页按阶段而非角色；成本显示三态。
8. 报告页分三层；草稿可导出带标识。
9. 原型标明「演示数据」；示例的时间、评分、预算、状态自洽（例如 Plan 额度、已用、本次申请三者能对上）。

不为了采用某种布局重做整个系统。

## 10. 优先顺序与验收

1. **统一业务契约**（本文）——验收：GBP spec 与 AM OS spec 引用本文规则编号，不再各自定义审批条件。
2. **补关键状态原型**（v3）——验收：AM 看每张异常卡能说出谁处理、下一步是什么。
3. **用 George 跑最小闭环**：草稿、退回、重审、批准、发布、核验；真实发布仍需具体内容批准。
4. **完善表现与报告交付**：按覆盖清单。
5. **再验证记忆与模型优化收益**：小范围对照，不同时全面启用。

最终目标：AM 表达目标后，系统能在授权内持续推进；遇到必须由人处理的事情，交来一项上下文完整、能直接完成的任务。
