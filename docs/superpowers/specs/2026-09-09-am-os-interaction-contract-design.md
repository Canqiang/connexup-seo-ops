# AM OS 交互契约 v1：每个可点击元素的目标、状态与返回

日期：2026-09-09
状态：待用户审阅
地位：`2026-09-09-am-os-business-contract-design.md`（业务契约）在界面层的对应物；`2026-09-09-am-os-data-workspace-design.md` 的页面按本文验收。本文是**建议采用的完整交互规则，不是现有功能已实现的说明**。
来源：用户 2026-09-09 重新核对原型 v3 后的意见：「商户列表」跳到工作台、「查看 Plan」停在商户区块、「纠正」跳回记忆区块、Performance / Audit / 报告共用同一锚点——静态展示可以，但不能验收真实使用流程。

## 0. 交付标准

> 每个可点击元素都有明确目标；每个提交都有成功、失败和处理中状态；每条业务链都能从入口走到结果，再返回原来的上下文。

每个按钮 / 入口都要写明六项：**目标对象、打开方式、是否改变状态、成功反馈、失败处理、返回位置。** 浏览器前进、后退、刷新、复制链接必须可用，不能只靠页面内按钮找回位置。

## 1. 路由与上下文模型（支撑「返回位置」与「复制链接」）

| 对象 | 路由 | 说明 |
|---|---|---|
| 工作台 | `/` | 当前 AM 待办 |
| 商户列表 | `/merchants?q=&status=&page=` | 搜索、筛选、分页进 URL；返回时恢复滚动与焦点 |
| 商户概览 / tab | `/merchants/:id`、`/merchants/:id/{plans,performance,audit,profile,reports}` | tab 是子路由，保持当前商户 |
| Plan | `/plans/:id` | 目标、范围、预算、任务、批准记录 |
| 任务列表 | `/tasks?merchant=&plan=&assignee=&status=` | 「查看全部任务」= 带筛选的列表 |
| Task | `/tasks/:id` | 人工任务、Agent 任务同一路由，按类型渲染 |
| 工作单 | `/work-orders/:id?step=review&version=2` | `step` 指定展开的步骤，`version` 指定产物版本；「审阅 v2」= 这个 URL |
| Audit | `/merchants/:id/audit`、`/audits/:runId`、`/audits/:runId/compare/:otherRunId` | 历史列表带 `?type=&status=&from=` |
| Performance | `/merchants/:id/performance?locations=&from=&to=&cmp=prev_equal&granularity=day` | 筛选全部进 URL；进关键词详情 `/keywords/:cohortId?from=&to=` 再返回仍是同一期间 |
| 报告 | `/reports?merchant=`、`/reports/:seriesKey/v/:n` | 打开指定历史版本 |
| 团队 | `/team`、`/team/models`、`/team/members/:id` | |
| 记忆 | `/merchants/:id/profile#facts`、`/memory/facts/:id/edit` | 「纠正」打开事实表单，不跳回列表锚点 |
| 对话抽屉 | `?drawer=chat` 叠加在商户路由上 | 关闭抽屉只去掉参数，保留对话与未提交输入 |

规则：身份型筛选（商户、门店）与期间都进 URL；刷新后重建同一视图；`Escape` / 关闭只回到上一路由，不重置筛选；列表页记录滚动位置与焦点元素 id，返回时恢复。

## 2. 全局导航与通用控件

| 按钮 / 入口 | 点击后的行为 |
|---|---|
| 工作台 | 打开当前 AM 的待办首页 |
| 商户 | 打开商户列表，不直接进入某个示例商户 |
| 任务与计划 | 打开任务 / Plan 列表，不直接进入某张工作单 |
| 数据与报告 | 打开跨商户数据中心 |
| 团队 | 打开成员与运行状态 |
| 商户名称 | 打开对应商户概览 |
| 返回商户列表 | 恢复之前的搜索、筛选、分页和滚动位置 |
| 商户内 tab | 保持当前商户，切换对应子页面 |
| 更多 | 就地打开操作菜单，只列当前身份和状态允许的操作 |
| 展开依据 / 历史 / 技术信息 / 团队 / 知会 | 就地展开，不创建任务、不触发 Agent |
| 问号 / 规则编号 | 打开对应字段解释或授权依据（业务契约 §2.4） |
| 关闭 / 取消弹窗 | 不提交；有未保存内容时提示 |
| 退出 | 有未保存内容时提示；退出成功后回登录页 |

## 3. 工作台、Plan 与商户页面

| 按钮 / 入口 | 点击后的行为 |
|---|---|
| 审阅草稿 / 审阅 v2、v3 | 打开对应工作单，并定位到指定审核 Task 和产物版本 |
| 查看工作单 | 打开完整工作单，不自动进入批准状态 |
| 去处理 | 根据该条待办打开实际 Task：价格确认、报告审核、权限处理分别进入不同页面 |
| 查看 Plan | 打开该 Plan 的目标、范围、预算、任务及批准记录 |
| 查看全部任务 | 打开已按当前商户 / Plan 筛选的任务列表 |
| 整体批准这 2 项 | 先展示变更内容、关联任务、额度变化；确认后提交整个批次，显示实际创建结果 |
| 退回 Plan / 变更申请 | 填写理由，交回 Orchestrator；不创建待批准的执行任务 |
| 编辑资料 | 打开资料编辑表单；保存内部资料不等于修改 Google 门店 |
| 团队对话 | 打开当前商户的对话抽屉，明确门店和 Plan 上下文 |
| 重新授权 | 打开该商户的连接管理，确认账号与资源范围后进入授权流程；回调验证成功才显示已连接 |

批准成功后显示「已授权 / 已入队」，不能直接显示「扫描完成」或「发布成功」（业务契约 P-C）。

## 4. GBP 工作单与人工 Task

| 按钮 / 入口 | 点击后的行为 |
|---|---|
| 草稿 / 审核 / 发布步骤 | 展开对应 Task，查看负责人、状态、产物和关联记录；三个 Task 各有独立 Task ID，工作单标题下写明「草稿任务 → 人工审核任务 → 发布任务〔包含远端核验〕」，审核的直接下游是发布任务 |
| 远端核验步骤 | 展开发布 Task 的验收阶段，不误导成第四个独立 Task |
| 历史版本 | 只读查看旧产物和旧审核；不能用旧页面批准当前版本 |
| 图片 | 打开大图、来源和授权信息 |
| CTA 链接 | 新标签页打开实际目标网址，保留当前审阅页 |
| 批准这一版 | 展示版本、完整产物、门店、发布时间；确认后服务端校验并保存批准，随后按规则调度发布 |
| 退回并说明 | 必填理由；提交后保留旧审核，新建下一轮草稿和审核 Task，显示新任务链接 |
| 上传凭证 | 文件选择或拖拽，显示上传进度、预览、失败及移除操作 |
| 提交确认结果 | 校验字段、日期、来源与凭证；成功后更新任务，显示哪些下游已解除等待 |
| 暂时受阻 | 填写原因、缺少什么和预计恢复时间；任务进入受阻，不关闭 |
| 请求协助 | 填写需要的协助；创建关联协助事项，原任务责任不自动消失 |
| 转交给… | 选择有资格的执行者并说明原因；执行中的任务需先安全停止或核验，再完成交接 |
| 取消任务 | 展示受影响的下游，必填理由；确认后触发重新规划（业务契约 E4），不留下永久等待 |

**审核页面打开后，如果产物被他人修改，提交批准必须失败并提示重新审阅，不能自动批准新版。** 实现：批准请求携带打开时的 artifact checksum 与 task row_version，服务端不一致返回 409，前端显示 ConflictBanner「内容已变化，请重新审阅」并重新载入，不重试。

## 5. 异常恢复

| 按钮 | 点击后的行为 |
|---|---|
| 开始核验 | 打开对应人工核验任务，展示原请求、历次读回及匹配候选；不是重新发布 |
| 查看读回列表 | 打开带查询时间的远端结果与差异 |
| 重新读取（新增） | 进行一次允许的只读查询，记录结果；不能触发新的写入 |
| 提交核验结果（新增） | 提交证据，由系统校验后推进；证据不足继续保持未知 |
| 审阅新版 | 打开新审核 Task，明确为什么原批准失效 |

不提供无证据的「当作成功」按钮。

## 6. 对话派单

| 按钮 | 点击后的行为 |
|---|---|
| 发送 | 提交意图，显示处理中；返回「已执行的范围内事项 / 待批准变更 / 需要补充的信息」三段 |
| @ Orchestrator / 内容 / 审计 / 关键词 Agent | 选择沟通对象，不因点击名字就立即创建任务或调用模型 |
| 交给我 | 将执行者意图设为当前 AM；若是接手已有任务，走正式转交校验 |
| 整体批准 | 使用与 Plan 页面相同的批准流程，不另建一套规则 |
| 退回 | 说明不接受的部分，由 Orchestrator 修订申请 |
| 关闭抽屉 | 保留对话与未提交输入；不取消已经开始的任务 |

消息中的 Task、Plan、工作单编号都可点击，打开对应真实对象（§1 路由）。

## 7. Audit：查看、执行、定时分开

| 按钮 / 入口 | 点击后的行为 |
|---|---|
| 查看最近诊断 | 打开最近一次有效 Audit，不重新运行 |
| 历史记录 | 打开当前商户的诊断列表，可按时间、类型、状态筛选 |
| 某次 Audit | 打开固定的该次结果，保留数据截至时间和执行 Task |
| 对比 | 选择另一份 Audit；检查范围与评分口径是否可比，再展示差异 |
| 问题 / 维度 | 展开发现、证据、缺口及关联任务 |
| 查看证据 | 打开这条发现实际引用的证据，不跳到通用资料页 |
| 立即诊断 | 配置范围和数据策略，展示预算 / 权限检查；提交后创建 Task，提供进度入口；同范围已有运行中的 Audit 时引导查看当前任务，不无提示再启动 |
| 查看运行进度 | 打开正在执行的 Audit Task |
| 周期设置 | 打开频率、时区、范围和额度表单；保存后显示下次执行时间 |
| 暂停 / 恢复周期 | 只影响后续调度；运行中任务另行处理，不能顺手取消 |
| 交给 Orchestrator 提计划 | 携带指定 Audit 和发现创建规划请求；已有相关 Plan 时先评估调整，避免重复创建 |

## 8. Performance：所有筛选都是可解释的查询

| 控件 / 按钮 | 点击后的行为 |
|---|---|
| 商户 / 门店 | 切换数据范围；清理不适用的筛选并明确提示 |
| 统计期间 | 打开日期面板，支持快捷周期和自定义起止 |
| 比较期 | 选择上一期间、去年同期或指定期间，显示实际日期 |
| 应用筛选 | 更新全部适用指标和图表；筛选保存到 URL，不调用 Agent |
| 日 / 周 / 月 | 改变展示粒度，不改变选定期间 |
| KPI 卡 / 趋势点 | 打开该指标在当前范围下的明细 |
| 关键词 | 打开该词的历史排名、评分来源、监测集与扫描记录 |
| 点阵图 | 打开该次扫描；允许选择符合比较条件的另一份扫描 |
| 数据状态 | 展开来源、覆盖日期、缺失、同步和补数信息 |
| 同步数据 | 发起明确的数据同步，展示进度；不购买新扫描 |
| 分析这段表现 | 把当前范围与期间交给分析 Task |
| 生成报告 | 带入当前筛选，进入报告配置；确认后创建报告 Task |
| 重置筛选 | 回到明确默认值，不突然换商户 |

例：从「George 的 8 月表现」进入关键词详情再返回，仍是 George 的 8 月，不重置为最近 7 天（§1：期间在 URL 里）。

## 9. 报告

| 按钮 | 点击后的行为 |
|---|---|
| 报告标题 / 查看报告 | 打开指定历史版本，不用最新数据重算。已交付或已审核的报告主操作是「查看报告」，旁边「下载」「交付记录」；只有待审阅的版本主操作才是「审阅」 |
| 审阅 | 打开完整报告与质量提示；进入页面本身不代表审核通过 |
| 审核通过 / 退回 | 保存对该版本的决定；退回产生修订工作，不覆盖旧版 |
| 导出草稿 PDF / PPTX | 导出明确标记未审核的版本；格式未就绪时说明原因 |
| 导出正式 PDF / PPTX | 下载指定已审核版本；尚未渲染时显示生成进度 |
| 记录交付 | 填写接收人、渠道、时间和凭证；只是记录，不自动发送 |
| 查看交付记录 | 打开历史记录；已交付报告默认显示此入口 |
| 发送给客户（以后接入） | 独立确认接收人和附件版本；与下载、人工记录分开 |
| 生成修订版 | 创建新版本，保留旧报告和交付记录 |

## 10. 记忆、团队与模型

| 按钮 / 入口 | 点击后的行为 |
|---|---|
| 录入事实 / 纠正 | 打开事实表单，要求来源、范围和有效期；保存新修订，不覆盖历史 |
| 确认为规则 | 确认规则内容、作用范围、有效期和权限；不能默认提升为项目级 |
| 拒绝候选 | 保存拒绝决定，不影响原始证据 |
| 仅本次适用 | 绑定明确的 Task / 工作单，不变成长期规则 |
| 设为验证中 | 配置假设、指标、期间和边界，再创建验证工作；不直接宣称有效 |
| 查看验证清单 | 只读展示原生记忆能力与隔离证据，不自动启用远端配置 |
| 成员 / 模型与成本 | 切换对应团队子页 |
| 成员、工作量、运行记录 | 分别打开成员详情、按执行者筛选的任务、具体执行记录 |
| Skill 名称 | 查看能力、引用和配置来源，不直接编辑共享 Skill |

## 11. 六种情况的统一验收

| 情况 | 要求 | 实现约定 |
|---|---|---|
| 正常 | 打开正确对象；提交后有真实结果反馈 | 成功反馈来自服务端读回，不是本地假设 |
| 处理中 | 按钮防重复提交；长任务可离开后回来继续查看 | 提交后按钮进入 busy 且不可再点；长任务给进度入口（Task 路由） |
| 失败 | 保留输入，给出原因，不靠整页刷新恢复 | 表单值不清空；`Notice` 显示服务端原因；可重试的才显示重试 |
| 结果未知 | 先查操作结果，不能自动重新提交发布或付费请求 | 超时 / 网络错误后先读回状态；发布与付费永不自动重试（业务契约 R5） |
| 状态过期 / 无权限 | 说明原因，服务端再次校验，不能只靠按钮置灰 | 请求带 row_version / checksum 前置条件；409 → `ConflictBanner` 重新载入；403 → 说明缺什么权限 |
| 返回 / 关闭 | 恢复筛选、分页、滚动和焦点；未保存内容有保护 | §1 路由；对话框关闭把焦点还给触发元素（现有 `ConfirmDialog` 约定） |

## 12. 原型如何表达交互契约（v4 起）

静态原型不能跑路由，但必须做到：

1. 每个按钮 / 链接带 `data-target="<§1 路由或本页锚点>"` 与 `data-effect="none|open|submit|expand|external"`，鼠标悬停显示「→ 目标 · 是否改变状态」。
2. 页内锚点必须指向正确对象：「商户」→ 商户列表区块，「任务与计划」→ 任务列表区块，「查看 Plan」→ Plan 详情区块，Performance / Audit / 报告各自独立锚点，「纠正」→ 事实表单。
3. 每个提交类按钮至少在一处画出六种情况（§11）的样例；v4 用「批准这一版」作样例面板。
4. 验收脚本检查：所有 `href="#…"` 都能解析到存在的 id；所有 `<button>` 都带 `data-target`。

真实实现中，本文每张表的每一行对应一个前端动作与一条 API 前置条件；写实施计划时逐行转成测试用例。
