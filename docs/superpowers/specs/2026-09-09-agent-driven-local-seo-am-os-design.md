# Agent 驱动的 Local SEO AM 操作系统：完整设计与原则 v1

> 产品定位：AM 带领人机混合团队，为多个商户持续完成 Local SEO 交付的操作系统。
>
> 一句话原则：对话表达意图，Plan 定义承诺与授权范围，Task 承载工作，Agent 和 AM 共同执行，证据证明交付，记忆和评测推动改进。
>
> 本文是待审阅的目标架构，不是上线说明。用户已确认 Agent 驱动、AM 作为参与者、Plan 范围内动态编排；已提出长期记忆、持续改进及多模型分工要求。本文补全的字段、状态、默认策略、界面与阶段门槛是建议设计，须经文档审阅与分阶段验证后实施。本轮不修改产品代码、数据库、远端 Agent、发布授权或定时任务。

## 1. 决策摘要

### 1.1 已确认的方向

1. 系统服务内部 AM，不把商户老板作为第一阶段的日常登录使用者。
2. AM 是团队参与者之一，可以派发、接收、执行、转交和审核任务；同时对商户服务结果负责。
3. Orchestrator 是 Core AI Server 上的 Agent，不只是一次性生成计划的接口。
4. AM 批准 Plan 后，Orchestrator 可以在批准范围内主动拆分、派发和推进低风险任务。
5. Plan 审批、具体内容审核、外部执行和完成验证是不同责任。
6. Task 直接关联 Plan；不让用户管理独立的 Plan Version，但必须保留批准内容和历史证据。
7. 需要商户记忆、工作上下文和反馈驱动的持续改进。
8. 使用多模型：高能力模型承担重要判断，经济模型处理边界明确的执行任务。
9. Agent/Skill 的定义、契约和依赖尽量归入 SEO Ops 项目管理；Core AI 作为外部运行平台。
10. 支持商户周、月、自定义周期的数据看板、Audit 展示，以及 PDF 和可编辑 PPTX 交付。

### 1.2 推荐路径与替代方案

| 方案 | 优势 | 代价与风险 | 决策 |
| --- | --- | --- | --- |
| 工作台 + Plan/Task + 对话派单 | 可追责、可恢复、可验收，同时保留自然语言入口 | 需要统一任务与授权模型 | 推荐 |
| 多 Agent 群聊为主界面 | 直观、有团队感 | 决策和成果容易埋在聊天里；容易模拟忙碌 | 仅借鉴协作表达，不作为事实来源 |
| 现有后台 + AI 助手 | 迁移成本较低 | AM 仍需手工串联所有步骤 | 可作为过渡，不作为目标形态 |

### 1.3 此次不是一次性重建全部系统

目标架构拆为六个可独立验收的子项目：

1. 工作与授权模型。
2. 事件驱动编排和人机交接。
3. Core AI 原生记忆接入、商户隔离与反馈评测。
4. 多模型路由和能力目录。
5. AM 工作台与商户工作空间。
6. 可复现数据看板与交付报告。

先验证动态编排是否有业务价值，再做一个商户的窄闭环；不同时重写所有业务模块。

## 2. 产品与工程原则

| 编号 | 原则 | 必须体现为的系统行为 |
| --- | --- | --- |
| P01 | Agent 驱动，而非 AM 手动启动每个 Skill | 事件能自动推进获授权的下一步；AM 只处理自己的工作和决定 |
| P02 | 结果导向，而非 Run 导向 | Run 成功、HTTP 200、生成文件均不直接等于 Task DONE |
| P03 | 一项业务事实有明确权威来源 | Plan/Task 状态由 SEO Ops 管理，外部数据由带来源的快照承载 |
| P04 | 统一协作，不统一权限 | HUMAN/AI 共用任务机制，但身份、工具权限和审批权明确区分 |
| P05 | Plan 是有限授权，不是空白支票 | 目标、门店、操作类型、预算、有效期和升级条件必须可校验 |
| P06 | 审批绑定具体对象 | 批准记录绑定对象、内容哈希、范围和有效性；修改后不能沿用旧批准 |
| P07 | 缺数据不等于零，不明确不等于允许 | 显示缺失原因；授权或归属不明时停止相关写入 |
| P08 | 外部结果未知时先核验 | 不因超时自动重发发布、扣费或创建请求 |
| P09 | 记忆可追溯、可纠正、可撤回 | 来源、适用范围、确认人、时间与失效条件可查看 |
| P10 | 学习不能扩大权限 | 经验不能自动变成预算、发布权或新的商户事实 |
| P11 | 模型是可替换的执行依赖 | Agent 职责与模型分离；模型切换不改变权限与验收标准 |
| P12 | 能用确定性代码完成的，不强行使用 LLM | 计算、同步、约束检查和发布核验优先由程序执行 |
| P13 | 成本按合格交付衡量 | 统计模型调用、重试、升级与人工返工，不只看单次 token 价格 |
| P14 | 状态和团队活动必须真实 | 不伪造 Live 进度、Agent 对话、人工发言或完成记录 |
| P15 | 同一数据快照，多种交付形式 | 网页、PDF、PPTX 使用一致的数值、来源和比较口径 |
| P16 | 逐步迁移、保留历史 | 不删除旧审批证据，不把目标设计冒充现有实现 |

业务效果原则：曝光、点击、排名、交付量与营收是不同指标；没有可核验的交易/归因数据时，不推算订单或收入，不把同期变化描述为已证明的因果关系。

## 3. 范围与非目标

### 3.1 第一阶段范围

- 当前已登录操作员作为人工 AM 身份；数据结构可支持多人，但不虚构已存在的多 AM 权限系统。
- 多商户列表与单商户工作空间；首个真实流程以 George 的店验证，具体身份与门店绑定在验证时读取。
- 接入与资料补齐、只读同步、Audit、关键词、排名、GBP 内容、人工审核、执行验证、报告。
- AM 主动派单与系统按已启用业务周期生成候选 Plan。
- 审批后的有限自动推进、事件恢复、任务交接、成本记录。
- 优先复用 Core AI 原生记忆；Ops 提供已确认事实/偏好/决定与隔离治理，不先建第二套经验引擎或全自动自我修改系统。

### 3.2 不作为默认范围

- 商户自助 SaaS、完整 CRM、广告交易系统、客户在线审批门户。
- 原型中所有社媒、创作者、付费广告和留存角色同时上线。
- 自动发布所有内容、自动购买所有 Local Falcon 扫描、自动发客户报告。
- 没有授权的共享 Agent/Skill 修改或跨项目代码变更。
- 全量聊天长期灌入模型、跨商户共享原始资料、在线自动微调模型。
- 让多个 Agent 随意互相调用，绕过任务、预算和权限服务。
- 为展示趋势编造历史数据或把旧快照填入缺失日期。

“先不做”不代表不能扩展。新增渠道必须先有服务范围、执行契约、授权和验收方式，再增加对应角色。

## 4. 商户交付 SOP

### 4.1 服务范围是工作的起点

每个商户建立服务配置，至少包含：

- 商户、门店、网站/账号等已验证资产绑定。
- 负责 AM、商户事实确认联系人。
- 服务项目、交付频率、目标周期、里程碑和验收口径。
- 预算、模型成本限制、付费扫描额度与来源配额。
- 已批准的品牌规则、发布方式、授权有效期。
- 时区、语言、服务暂停/结束规则、报告接收约定。

服务合同或客户文档中的承诺必须核实确认状态后录入，不能把“商家版草稿”当成已签约事实。不同商户的关键词数量、内容频率和服务渠道可以不同，不全局写死为 Top 20 或每月四条。

### 4.2 全业务流程

| 阶段 | 主要输入 | Agent/系统工作 | AM 工作 | 关键输出 |
| --- | --- | --- | --- | --- |
| 接入 | 名称、门店、可选 Merchant ID、可选官网 | 预填、检查身份与权限、建立资料缺口任务 | 确认服务范围、事实来源与绑定 | 商户服务配置、资料清单 |
| 事实准备 | GBP、菜单、图片、客户确认 | 来源对照、识别冲突、整理品牌档案 | 解决经营事实冲突、向商户补资料 | 可追溯商户事实 |
| 基线与诊断 | GBP/GSC/排名/网站可用证据 | 并行取数、Audit、关键词和覆盖检查 | 审阅重要缺口与风险 | 冻结快照、Audit、候选机会 |
| 制定 Plan | 服务目标、证据、历史工作 | 提出周期计划、初始任务、授权需求 | 批准目标、范围和资源限制 | 获批 Plan |
| 持续执行 | Plan、依赖、事件、记忆 | 派单、生成成果、校验、调整范围内工作 | 完成人工 Task、审核、处理异常 | 已验证交付物 |
| 周期报告 | 冻结数据、完成记录、未解决问题 | 计算、解释、生成报告与文件 | 审核业务表述、决定交付 | 网页/PDF/PPTX 报告 |
| 复盘与下一周期 | 结果、AM 反馈、客户反馈 | 提炼候选经验、提出新 Plan | 确认长期规则与策略变更 | 经验记录、新周期 Plan |

执行采用真实依赖 DAG，而非所有步骤串行：GBP 只读表现同步不必等待关键词生成；网站缺权限只阻塞需要该权限的工作；缺 Audit 不阻塞已经明确的补资料任务。

### 4.3 新建商户

- Merchant ID 和官网均为选填；没有官网可以进入“网站建设需求”，不编造站点。
- 有 Merchant ID 时，先验证所属商户与门店，再同步；不能按名称自动猜绑定。
- “新建”后后台启动可用的只读准备流程，页面显示真实状态。
- 没有授权的数据源生成补充权限任务，不使整个商户创建失败。
- 启动诊断与同步不等于授权公开修改。
- 诊断依据不足时输出证据缺口和初步计划，不伪造完整审计分数。

## 5. 团队模型：AM 与 AI 都是参与者

### 5.1 三种责任必须分开

| 概念 | 定义 |
| --- | --- |
| 商户负责 AM | 对服务进度、客户沟通和交付结果负责 |
| Task 当前执行者 | 对当前任务交付负责，同一时刻最多一个明确执行者 |
| 审批者/验证者 | 根据权限作决定或依据证据验收，不必等于执行者 |

AM 是人类参与者，不是被模型模拟出来的角色。AI 不得生成带 AM 身份的批准、客户确认或已执行声明。

### 5.2 参与者的目标字段

- participant_id、kind：HUMAN / AI_AGENT。
- display_name、role、capability_refs、enabled。
- merchant_scope、allowed_task_types、authorization_policy_ref。
- capacity、availability、current_workload。
- 人类关联已认证用户；AI 关联现有 SEO Ops Agent 注册记录及环境绑定。
- 技术服务可作为事件 actor，但不伪装为人或 LLM Agent。

这是统一读模型与协作契约，不要求另起一套重复的 Agent 注册表。

### 5.3 首批能力角色

| 角色 | 责任 | 典型产物 |
| --- | --- | --- |
| Orchestrator | 规划、分工、处理事件、提出调整 | Plan、决策提案、升级请求 |
| 商户研究/资料 Agent | 事实整理、资料缺口、品牌规则 | 商户事实候选、确认任务 |
| Audit Agent | 基于证据审计、解释问题与缺口 | 结构化 Audit、报告 |
| Keyword Agent | 使用项目确认的 Skill 研究、评分与筛选 | 关键词集、评分依据、监测建议 |
| GBP 内容 Agent | 根据已确认事实生成内容与素材要求 | 文案/图片/CTA 草稿 |
| 网站 SEO Agent | 提出或准备授权范围内的网站优化 | 修改建议、补丁或验收清单 |
| 分析与报告 Agent | 解读冻结数据、生成报告叙事 | 报告内容、图表说明、下一步建议 |
| AM | 商业判断、资料确认、审核、沟通、人工执行 | 决定、反馈、确认依据、交付记录 |

角色是能力分工，不等于必须创建八个远端 Agent。可复用经核验的实现，但不能因名称相似就绑定；内容生成和发布应使用隔离的工具权限。

## 6. 领域模型

以下是逻辑契约，不是现行数据库迁移脚本或已实现 API。

### 6.1 核心对象及关系

~~~text
Merchant / Location / Asset Binding
              │
      Service Configuration
              │
             Plan ─── Approval / Change History
              │
             Task ─── Dependencies / Assignments
              │
          Execution ─── Core AI Run（真实存在时）
              │
       Artifact / Verification
              │
       Event → 下一轮编排
              └→ Feedback → Memory Candidate → Evaluation
~~~

Report 引用冻结 Snapshot 和相关交付；Memory 引用原始事实/决定/反馈，不另造一份任务状态。

### 6.2 Plan：目标、承诺与有限授权

核心字段：

| 分组 | 字段建议 |
| --- | --- |
| 身份 | id、merchant_id、location_scope、owner_am_id |
| 目标 | objective、success_criteria、service_scope_ref、period_start/end、timezone |
| 依据 | evidence_refs、input_snapshot_ref、source_agent_id、source_run_id |
| 工作 | 初始任务提案、当前正式任务引用、交付里程碑 |
| 授权 | allowed_action_types、asset_scope、budget_limits、approval_policy_ref、valid_until |
| 历史与并发 | state、row_version、approved_snapshot_hash、approval_ref、change_events |

推荐状态：DRAFT → AWAITING_APPROVAL → ACTIVE → COMPLETED；另有 REJECTED、PAUSED、CANCELLED。属于目标业务状态，迁移时与现有 OPEN/CLOSED 显式映射。

- Task 业务来源只有 plan_id，不要求用户选择 Plan Revision。
- 并发版本、Schema 版本、批准快照、Artifact 版本仍然需要。
- 获批范围内新增任务，保存授权依据和新增原因，不要求重批整个 Plan。
- 修改目标、预算、资产范围、服务承诺或授权策略，需要新的明确批准记录。
- 批准范围变更不能使旧批准自动覆盖新内容；撤销权限后，未派发写入停止。
- 同一商户可以有多个明确范围的 Plan，但跨 Plan 检查重复工作和资源冲突。
- 周/月是计划周期，不要求每周自动重生成全部关键词或重做所有 Audit。

### 6.3 Task：独立业务交付单元

核心字段：

- id、merchant_id、location_id、plan_id。
- task_type、workflow_version、title、objective、parameters。
- rationale、expected_outcome、evidence_refs。
- assignee_type、assignee_id、priority、scheduled_start、due_at。
- acceptance_criteria、verification_policy、required_authorization。
- status、row_version、definition_checksum。
- related_task_id / replaces_task_id（需要时）、业务去重标识。
- created_by、creation_decision_ref、created_at、完成/取消时间。

Task 有独立交付、交接或验收价值才拆分。API 分页、模型 token 流和内部自检通常属于 Execution，不成为独立业务 Task。第一版不强制新增多层父子任务树；依赖关系和相关任务引用足够时优先复用。

人工临时派单采用轻量单任务 Plan，避免脱离统一来源；自然语言请求可生成草稿，但不能因为一句含糊“帮我弄一下”直接触发公开修改。

### 6.4 状态与就绪性

复用当前状态基础，按任务类型定义合法路径：

~~~text
PENDING → PREPARING → AWAITING_APPROVAL → EXECUTING → VERIFYING → DONE
异常：NEEDS_ATTENTION
终止：CANCELLED
~~~

不是所有 Task 都经过所有阶段。人工审核 Task 在自己的 EXECUTING 阶段等待 AM 决定；被它阻塞的发布 Task 保持 PENDING，并显示 WAITING_DEPENDENCY / WAITING_AUTHORIZATION，避免两个相互等待的审核。

readiness 派生计算，不允许独立手改：

- READY、UNASSIGNED、WAITING_DEPENDENCY、WAITING_INPUT。
- WAITING_AUTHORIZATION、NOT_DUE、BUDGET_BLOCKED、PROVIDER_UNAVAILABLE。
- 同时保留多个 blocker，前台展示首要原因与完整详情。

审核 Task 可以因“已作出拒绝决定”而完成。后续发布依赖必须检查“批准结果及有效授权”，不能只检查审核 Task.status = DONE。

### 6.5 Execution、Artifact、Approval 与 Event

| 对象 | 必要内容与约束 |
| --- | --- |
| Execution | 独立尝试、执行者、实际模型、固定输入、费用、错误、幂等键、外部引用；人工不伪造 Run ID |
| Artifact | 来源 Task/Execution、类型、不可变内容/版本、hash、存储引用、可见性 |
| Approval | 审批对象、内容 hash、商户/资产/操作范围、决定、真实审批者、有效期与撤销 |
| Verification | 验收规则、证据引用、结果、执行者、时间；不能由一句成功声明代替 |
| Event | event_id、entity、actor、occurred_at、causation_id、correlation_id、payload_ref |
| Feedback | 关联成果和决定、原因分类、修改建议、是否具有长期适用性 |

原始 Run/执行结果不能因当前配置、任务转交或记忆更新而改写。

## 7. Orchestrator 的持续推进机制

### 7.1 输入上下文

每次决策读取一个有版本界限的 Context Pack：

- 当前商户与门店的已确认事实、服务配置。
- Plan 的有效授权与批准快照。
- 相关 Task、依赖、已有成果与未解决 blocker。
- 本次事件及已处理游标。
- 相关数据快照、证据缺口与时效。
- 本次检索到的适用记忆及其版本。
- 可分派参与者、能力、可用性和预算余额。

保存输入引用及 hash，以便复现业务上下文；原生动态记忆的实际注入另记录可用证据，不能因此声称模型输入全量可复现。不要传入所有商户历史、完整无关聊天、凭据或默认全部工具。

### 7.2 有限决策协议

Orchestrator 输出 DecisionProposal，允许命令建议：

- CREATE_TASK、UPDATE_PENDING_TASK、ASSIGN_TASK。
- REQUEST_HUMAN_INPUT、REQUEST_APPROVAL、PROPOSE_PLAN_CHANGE。
- CANCEL_PENDING_TASK、REQUEST_RECONCILIATION。
- NO_ACTION，附解释和下次需要的事件。

禁止模型直接 SET_DONE、APPROVE_AS_HUMAN、GRANT_PERMISSION 或调用任意 SQL。未实现/未登记的任务类型拒绝执行，不自动转为“通用任意任务”。

每条命令包含目标、理由、证据、预期 Task/Plan 并发版本和幂等依据。系统按已注册操作类别核验风险，不信任模型自己声称“低风险”。

### 7.3 应用提案

1. 验证结构、引用、商户隔离、任务类型和 DAG 无环。
2. 检查 Plan 是否 active、有效，操作是否落在授权集合内。
3. 检查当前版本、正在执行的任务、业务去重和预算。
4. 对完整决策批次做原子性校验与本地状态提交。
5. 同一事务写出待派发事件；远端操作不放进数据库事务。
6. 由持久化 worker 执行，并在派发前再次检查权限、批准和预算。
7. 记录接受/拒绝原因；版本冲突读取新状态后重新决策，不能重复提交旧提案。

### 7.4 触发与节流

- 来源：Task 完成/失败/阻塞、AM 决定、新证据、到期检查、明确的业务周期。
- 同一 Plan 的决策串行化；相关短时间事件合并，避免每条日志触发 LLM。
- 工作推进优先由确定性依赖规则处理；只有需要判断时调用 Orchestrator。
- 为单商户设置决策次数、连续无进展次数和日预算上限；第一版上限必须显式配置后才可自动启用。
- 达到限制后进入需要处理，不静默继续烧费用。
- 月报/周计划等为应用内业务 scheduler；本文不创建 Codex 自动化。
- 自动化默认关闭，按商户启用；启用后不自动无限补跑历史周期。

## 8. 执行可靠性与异常恢复

### 8.1 可靠性目标

本地状态提交可保证事务一致性；跨网络不宣称 exactly-once。采用至少一次事件投递、幂等处理、唯一约束和外部核验实现尽可能不重复的业务效果。

- outbox 保证状态提交后有可恢复派发事件。
- inbox/processed-event 记录消费者去重。
- worker lease 与心跳支持崩溃恢复，但 lease 过期不证明外部请求未执行。
- 每个 Task/Stage 只允许一个当前有效执行；旧执行 UNKNOWN 时阻止新的写尝试。
- 业务去重结合 merchant、asset、work kind、scope、period/问题证据；明确重做使用新的意图记录，不能靠文本相似度硬去重。
- 归档商户和暂停 Plan 停止新执行，保留既有历史；正在运行/未知的外部操作必须对账。

### 8.2 恢复矩阵

| 情况 | 处理 |
| --- | --- |
| 只读请求临时失败 | 有限退避重试，保留错误和最近成功快照 |
| 结构化输出不符合契约 | 返回明确校验反馈做有限修正；失败后升级或转人工，不硬凑默认字段 |
| 权限过期/商户绑定不明 | 阻塞受影响工作并创建处理事项 |
| 公开写入超时 | Execution = UNKNOWN；查询现有结果，不自动重建 |
| 找到可唯一匹配的实际结果 | 绑定外部资源，运行独立验收 |
| 无法证明存在或未创建 | 保持 NEEDS_ATTENTION；AM 按对账政策处理，不能直接点“当作成功” |
| Task/Plan 并发冲突 | 不覆盖他人修改，重新载入后决定 |
| 运行中转交 | 先确认停止/终态/核验，再建立新 Assignment；历史执行者不变 |
| 上游成果被撤回或内容改变 | 下游就绪性重算；旧内容批准不再授权新内容 |

## 9. 授权与审批

### 9.1 默认权限矩阵

| 动作 | 默认规则 |
| --- | --- |
| 商户范围内只读分析、草稿、内部校验 | 获批 Plan 与能力权限内自动执行 |
| 范围内新增/拆分任务、调整未开始任务顺序 | 系统检查后自动应用并留痕 |
| 给 AM 分配资料、审核、沟通 Task | 可以自动分派，不能代 AM 提交 |
| 变更服务目标、期限承诺、费用或资产范围 | 新批准后生效 |
| 购买 Local Falcon 扫描 | 单独额度/预算检查及适用审批；同步已有报告不算购买 |
| 发布 GBP、回复评价、修改网站/经营资料 | 第一阶段默认逐项内容审批；只有显式配置并批准的有限政策才可例外 |
| 对客户交付报告 | 第一阶段由 AM 明确决定；生成报告不等于已发送 |
| 修改全局 Skill/模型政策/授权策略 | 经评测与授权发布，不能在线自行更改 |

这不是宣称所有公开操作永久必须逐项审批。未来可配置商户认可的规则化授权，但必须有明确操作范围、事实规则、额度、有效期和撤销路径，不能从沉默或历史批准推断。

### 9.2 审核与发布

- 审阅完整文案、图片、链接、目标门店和发布时间/时区。
- 批准时绑定具体 Artifact manifest/hash；生成新图片或修改 CTA 都触发重新检查。
- 服务端验证当前登录身份，不接受模型提交的“AM 已批准”文本。
- 审核完成与发布授权分开存证；拒绝、要求修改也是有效审核结果。
- 发布前重新确认授权未撤销、内容未变、目标绑定未变。
- 人工执行仍需提交可核验外部证据；“我已发布”可启动验证，但不能直接完成业务。

## 10. 记忆系统：优先复用 Core AI 原生能力

### 10.1 架构修正与已核对证据

用户补充的 UAT 截图显示 Agent 配置已有 Enable memory：开启后从完成的运行学习，并用于后续运行；界面提示 Publish 后应用于 live runs。因此，不再假设 SEO Ops 需要重建记忆提取、存储、检索和注入引擎。

本次只读检查本地 Core AI 源码，HEAD 为 e9837b1a（不是 UAT 部署版本证明）：

- AgentMemory 持久化 agent_id、layer、content、source_trace_ids、创建/更新时间。
- 分层包括知识、方法和轨迹；ConsolidationJob 从历史完成 trace 提取方法/轨迹，知识层不由该提取任务自动生成。
- AgentRunBuilder 读取 publishedConfig 中的 enableMemory，挂载 search_memory 和记忆注入逻辑。
- AgentMemoryExperimentService 支持层选择、topK、注入概率、排序策略与注入记忆 ID 记录。
- AgentMemoryWebServiceImpl 有列表、删除、实验配置与实验运行查询能力；这些本地方法存在不等于 UAT 路由、权限和完整操作链已经验证。
- 核对的查询主要按 agent_id 过滤；AgentMemory 对象没有 merchant_id/location_id 字段。不能据此假定同一个 Agent 的不同商户调用天然隔离。
- 本地兼容逻辑对 enableMemory = null 的历史对象视为开启，只有显式 false 关闭；新建服务逻辑又会明确写入布尔值。适配器必须核验实际 published config，不能只看编辑页或把未配置当关闭。
- 记忆提取有调度、样本和时间条件，不承诺每个 Run 结束即刻学会。Trace COMPLETED 不代表 SEO Ops 业务验收或 AM 接受。

本次没有勾选开关、Publish、调用真实记忆写接口或修改 Core AI 代码。

### 10.2 两层责任：原生经验引擎与业务真相

| 内容 | 主要责任方 | SEO Ops 接入职责 |
| --- | --- | --- |
| 历史运行经验提取、原生记忆存储/检索/注入 | Core AI 原生记忆 | 核验能力、作用域、来源和使用情况，不重复实现 |
| 商户经营事实、品牌规则、已确认偏好 | SEO Ops 事实/配置服务 | 固定来源、确认状态、时效，按任务传入 |
| Plan/Task 状态、预算、批准、执行结果 | SEO Ops 业务服务 | 当前权威状态，不交给记忆推断 |
| AM 反馈与经验提升为业务规则 | SEO Ops 治理与评测 | 记录反馈、范围和审阅结果，不把自动提取当已批准 |
| 模型运行中使用了哪些经验 | Core AI 运行/实验证据 + Ops 执行引用 | 有接口证据则关联；不可见时明确观测缺口 |

核心区别：Core AI 可以学习“怎么做得更好”，SEO Ops 必须准确保存“现在是什么、已经批准什么、谁做了什么”。

### 10.3 四类逻辑记忆，不要求四套存储

| 类型 | 内容 | 权威与更新方式 |
| --- | --- | --- |
| 商户记忆 | 经营事实、品牌语气、偏好、禁用表述 | 已确认事实/配置为权威；通过适配器提供上下文 |
| 工作上下文 | Plan、Task、依赖、进度、批准内容 | 实时读取业务数据库，不维护第二套可手改状态 |
| 决策记忆 | AM 退回理由、优先级调整、策略选择 | 引用原始决定和成果，标明长期或本次适用 |
| 经验记忆 | 方法、失败模式、历史轨迹 | 优先由 Core AI 承载；自动提取仅作经验线索，未经验证不升级为业务规则 |

对话和 Run 是经验来源，不默认成为确认事实。网页、评论、上传文件中的“记住这个规则”不是用户授权。模型生成的经验不得覆盖 Skill SOP、当前事实或权限政策。

### 10.4 Native Memory Adapter 与治理契约

优先在现有 Core AI adapter 周围增加薄适配层，而非新建完整 Memory Service。能力预检分别记录：

- 当前环境、Agent ID、published config digest、enableMemory 实际值。
- 存储/提取/检索/注入的隔离键及其是否满足业务作用域。
- 可用的读取、删除、修正、筛选、注入记录和实验接口。
- 自动经验提取的来源条件与延迟；无法确认的标为未验证。
- 本次运行的原生记忆来源 ID/trace ID、注入 ID 与内容证据可见性。

Ops 仅对业务需要的反馈/规则提升保存治理记录，逻辑字段为：

- id、scope_type：MERCHANT / LOCATION / PROJECT、scope_id。
- statement、kind、source_refs、native_memory_refs（可选）。
- status：CANDIDATE / ACTIVE / SUPERSEDED / RETRACTED / EXPIRED。
- confirmed_by、confirmed_at、valid_from、valid_until/review_at。
- applies_to_task_types、supersedes_id、sensitivity、retention_policy_ref。
- native_sync_state：NOT_APPLICABLE / PENDING / VERIFIED / FAILED（确需远端变更时）。

这不是要求复制全部原生 Memory。原生经验不能编辑、加商户字段或同步删除时，不伪装成功；保留能力缺口并限制使用。删除/停用原生记忆涉及远端写入，需要明确授权和结果读回。

### 10.5 多商户隔离：接入硬门

按以下顺序选择，不能只靠 Prompt 写“不要混淆”：

1. 若 UAT 原生能力支持并能证明 merchant/location namespace，所有提取、存储、自动注入与 search_memory 路径都绑定该 scope。
2. 若仅按 Agent ID 隔离，可在资源所有权与成本确认后，为需要原生学习的商户创建专用运行实例；复用同一角色/Skill 定义，不要求 AM 手工维护每家店的一整套提示词。
3. 若不能证明隔离，跨商户共用 Agent 的自动学习不能接收商户私有信息。先使用已确认的显式业务上下文；共享原生经验仅限经过验证的去标识化方法，并检查既有记忆池是否已含商户资料。
4. 项目级跨商户编排如读取多个商户，应走专门的授权上下文；其经验不能自动回流到普通单商户 Agent。

仅在调用请求增加 merchant_id 字段不等于后端会使用它过滤记忆。禁用实验注入也不一定关闭 search_memory 或提取；必须同时验证全部路径。

先以单商户隔离试验验证，不在本次设计落盘时自动创建实例、清空记忆或切换开关。若发现现有共享池可能包含私有信息，停止新的受影响调用并提出处理方案，不能自行删除全部历史。

### 10.6 更新、反馈与使用

1. AM 的原始反馈先关联业务 Task/Artifact；确认其本次适用还是长期规则。
2. Core AI 可自行提取方法/轨迹，但这不等于已通过 AM 审批；作为低信任经验使用并继续做确定性校验。
3. 将经验提升成商户规则、共享方法或 Skill 变更时，才进入候选→验证→确认/拒绝流程。
4. 新运行的业务 Context Pack 保存已确认事实/规则及其版本；原生动态注入实际使用的记忆引用在可观测时补入执行记录。
5. 同一 Agent 切换模型原则上可以复用其原生池，仍需验证实际接口行为；改为不同远端 Agent ID 时，不假设原生池自动共享。
6. 多模型配置若通过不同 Agent 实例实现，用相同业务上下文保持事实一致；原生经验跨实例复用需显式映射、隔离校验与授权，不复制整个商户池来解决路由问题。
7. 原生接口不能提供完整记忆快照时，不声称模型输入完全可复现；记录缺口，审批与业务判断仍依赖固定输入。

### 10.7 纠正、撤回、时效与隐私

- 当前已确认事实优先于历史摘要；价格、营业时间、活动等按有效期复核。
- Ops 撤回业务规则立即影响后续 Context Pack；若同一内容仍在原生池，必须验证原生失效/删除，未完成前限制受影响记忆路径，不能宣称“一处撤回全部生效”。
- 原生删除历史经验不改写已完成执行的证据；需要留存的执行引用按访问政策保存。
- 商户归档不等于销毁审计历史；敏感信息的保留/删除由明确政策决定，索引/摘要同步处理。
- Secret、token、完整认证头不进入记忆、Git、提示词或可见日志。
- AM 界面区分“Core AI 自动提取经验”与“已确认商户规则”，不统一打“已验证”标签。
- 若政策要求禁止从试验中学习，必须使用隔离实例或已验证的关闭提取/注入方式，避免 shadow 数据污染正式记忆。

### 10.8 最小原生能力验证

在任何共享 Agent 自动记忆启用前，验证：

1. 编辑态与 published config 的生效边界。
2. 一次符合提取条件的测试是否留下有来源的记忆，延迟和前置条件是什么。
3. 后续运行是否实际注入/检索了它，而非仅开关显示开启。
4. A 商户的特有信息能否被 B 商户调用读取；要求所有注入和搜索路径隔离。
5. 修改/撤回后旧经验是否仍影响后续运行。
6. 切换模型或 Agent 实例时，记忆作用域与使用记录是否符合设计。
7. 关闭记忆是否同时影响提取、自动注入、搜索工具；历史记忆是否保留。

验收记录区分“界面可配置”“源码存在”“UAT API 可用”“真实运行有效”“商户隔离通过”。不把前两项当作后面三项的证据。

## 11. 持续优化与评测

### 11.1 改进闭环

~~~text
实际执行 → AM/客户反馈 → 候选经验或配置变更
      → 回放与留出测试 → 审阅/启用 → 小范围观察
      → 保留、修订或回退
~~~

先改善上下文、规则、工具契约与模型路由，不把在线微调作为第一步。

### 11.2 学习不能越过的边界

- 一次修改不自动成为永久偏好。
- 单次发布批准不自动成为长期发布权限。
- 较高模型自评分不等于 AM 接受或业务验收。
- SEO 同期增长不等于某条策略造成增长。
- 不能为了提高通过率降低验收规则、隐藏失败或删除反例。
- 不允许 Agent 自行发布新的全局 Skill、提示词、预算或工具权限。

### 11.3 评测资产

每个评测案例保存输入快照、有效政策、期望允许/禁止动作、模型与 Skill 修订、记忆包、真实输出、校验结果、AM 裁定与成本。

采用固定基础集加留出变体。按任务类型评测，不用单一总分掩盖安全错误。候选经验测试应包含“不应套用”的反例，例如 George 的偏好不能作用另一商户。

### 11.4 运行指标

- 合格交付率：满足该任务验收标准的交付 / 到验收阶段的交付。
- AM 修改率：需要 AM 修改或退回的成果 / AM 审阅成果。
- 重复错误率：已确认反馈之后再次发生同类错误的比例。
- 人工协调时间：采样记录主动操作时间，不把等待商户响应算作 AM 劳动。
- 无进展循环、重复派单、未授权尝试、未知写入数量。
- 总交付成本：调用 + 重试 + 升级 + 工具费用；人工成本有记录时单列。
- 按模型/能力/商户类型分组，避免容易任务占比变化造成“变聪明”的假象。

## 12. 多模型分工与 Agent/Skill 管理

### 12.1 分工不是“一个角色永久绑定一个模型”

| 工作 | 建议默认 | 升级/退出条件 |
| --- | --- | --- |
| Plan 制定、复杂异常、策略调整 | 高能力模型 | 缺事实转人工，不因模型强而猜测 |
| Audit 综合、证据冲突、效果解释 | 高能力模型 | 数据不足输出边界或缺口 |
| Post/报告初稿、常规修改 | 经济型模型 | 有限修正失败或复杂判断时升级 |
| 分类、提取、格式整理 | 小模型或代码 | 契约/准确率不满足则换路径 |
| 数据同步、指标计算、授权、发布核验 | 确定性程序 | 失败按恢复规则处理，不用 LLM 猜结果 |

本文不指定未经实测的供应商型号、价格或“最好模型”。按当前 Core AI 可用能力、数据边界和真实任务评测选择。

### 12.2 路由规则

ModelPolicy 包含：

- capability_key、task/stage、default_profile、fallback_profiles。
- required_features：结构化输出、工具、多模态、上下文需求。
- approved_provider_scope、数据敏感性限制。
- max_attempts、timeout、token/cost ceilings、escalation_conditions。
- policy_digest、启用人、启用时间。

先过滤权限/能力/数据处理条件，再考虑成本。输出验证失败时可携带具体错误做有限修正；缺授权、缺事实不能靠升级模型解决。

高风险规划模型不可用时，默认暂停相关决策，不静默降级。经济模型升级必须在预算和允许列表内；预算不足转人工处理。

### 12.3 成本与运行证据

- 派发前预留预算，完成后按实际 usage 结算并释放剩余。
- 费用未知单独标记，不能记录成零；未结算预留继续占用额度。
- 队列检查与实际执行前检查共同防止并发超支。
- 记录请求模型、实际返回模型、provider、latency、usage、费用来源与估算标记。
- 若 Core AI 不能逐次指定模型，使用预配置并核验的 Agent/profile 绑定；不能假设接口支持 model 参数。
- 上下文压缩保留任务合同、批准范围、关键事实和引用；不能为省 token 删掉安全约束。

### 12.4 项目统一管理

SEO Ops 仓库管理：

- Agent 职责、提示词定义、Schema、Skill 引用、工具权限。
- 模型路由政策、评测案例、回归结果、发布/回退记录。
- 各环境外部 ID 映射与非敏感配置；凭据在服务端安全配置中。
- Agent/Skill 的已观测 digest 和漂移状态。

Core AI 负责远端运行。共享 Skill 存引用和核验信息，不擅自移动、覆盖或删除；专用对象经所有权确认后再同步定义。工作台“active”只说明注册状态，不证明远端可用、绑定正确或本次实际调用。

## 13. AM 工作台与交互设计

### 13.1 信息架构

建议导航：工作台 / 商户 / 任务与计划 / 数据与报告 / 团队。

- 工作台：跨商户需要处理事项。
- 商户：进入具体服务与事实空间。
- 任务与计划：跨商户检索、派单、排期、计划审批。
- 数据与报告：历史看板、Audit、周期交付。
- 团队：人和 AI 的职责、工作量、能力及运行健康。

这是目标导航，不立即覆盖现有路由。顶栏保留操作员区域，不恢复用户已要求删除的“当前工作范围 / 全部商户”装饰区域；业务筛选放在相关页面标题下。

### 13.2 首页：我的工作，而非所有机器日志

四类内容：

1. 需要我决定：Plan、发布、范围/预算变更。
2. 分派给我：资料确认、商户沟通、人工执行。
3. 需要关注：延期、授权过期、外部结果未知、数据质量。
4. 仅知会：已验证完成、计划内调整、报告已准备。

排序优先真实业务严重性、截止时间、阻塞影响；模型建议不能单独决定通知优先级。相同问题聚合为一个事项，并链接关联 Task，防止消息轰炸。

每条工作项显示商户/门店、目标、负责人、截止时间、影响、成果/依据和唯一明确的下一步。AM 可以稍后处理，但不能通过隐藏事项解除发布阻塞。

### 13.3 商户空间

- 概览：目标、服务范围、负责 AM、里程碑、风险。
- 计划与任务：周期 Plan、依赖、进展、调整记录。
- 商户资料与记忆：已确认事实、来源、冲突、偏好、待确认记忆。
- 数据与诊断：GBP、GSC、关键词、排名、Audit。
- 成果与报告：草稿、批准内容、已验证发布、周期报告与导出。

### 13.4 Task 详情

主区：做什么、为什么、当前成果、验收、下一步。

侧区：负责人、截止时间、前后置任务、批准状态、成本与证据。

历史：真实执行/转交/决定事件；模型和技术 trace 默认折叠。去掉不能服务当前操作的内部元数据大表单，不靠标签堆砌替代任务结构。

### 13.5 对话派单

- 全局输入先解析商户范围；范围不明确时不能跨商户执行。
- 商户/Task 内对话自动带当前范围，并明显显示。
- @ 某个 Agent 表示分配意图；仍需校验其能力和权限。
- 输入“交给我”可申请接手，运行中任务先处理旧执行。
- 对话生成任务提案，持久化成功后才显示“已派单”。
- 未开始、处理中、等待人工、失败、未知与完成分别展示；不能只给一个转圈。
- 不展示模型私有推理链；展示可审计的决策摘要、依据与命令结果。

### 13.6 原型的采用与舍弃

采用：Needs You / FYI、参与者可见、成果预览、团队协作感、明确下一步。

调整：从店主视角转为 AM 跨商户工作台；团队名单为辅助入口，不挤占全部主导航。

舍弃：随机 Live 事件、硬编码群聊、忽略澄清答案、点击审核立即 DONE、未回复自动批准、未经证据支持的 SEO 因果叙事。

视觉原则：统一间距/字体/按钮高度、主次操作、可访问的焦点与对比度；状态不只靠颜色；有限动画支持 reduced-motion。长菜单和关键词使用有界列表/分页，操作栏保持可见；图例靠近图表，字段问号可点击且支持键盘。具体视觉 token 和布局另做原型验收，不在本文件擅自替换现有设计系统。

## 14. 数据、Audit 与关键词

### 14.1 数据来源与身份

- GBP 表现、评价、Posts、菜单按实际可用接口分别标记。
- GSC 默认是 property/网站范围，不能无依据分摊到单门店。
- Local Falcon 是本地网格测量来源，不是我们目标关键词的权威来源。
- FBR 关键词是候选/持久化来源，需保留生成 Skill、评分和确认信息。
- Merchant ID、GBP Location ID、storeCode 和内部 location_id 分别存储，不能互换。
- 多门店聚合先解决重复和归属，不能按名称或第一个返回结果选门店。

### 14.2 同步与生成分开

页面读取库中最近有效数据；同步失败保留旧快照并标记陈旧与错误，不把失败包装成空数据。

同步周期按数据源、商户和费用配置。UI 状态轮询不等于重新向 FBR 同步；业务只读同步不等于创建付费扫描。来源默认周期在实施前核对现有配置，本设计不默认把所有源改为每小时或每天。

关键词默认读取已有有效集合；缺失或用户明确要求重新生成时调用已核验的项目 Skill。重新生成产生候选集合，不静默覆盖已批准监测集。评分缺失时不能把全部关键词当作 Top 20。

监测集合绑定确定的关键词集合/评分、选择规则及批准记录；数量按服务配置。重新生成不自动发起 Local Falcon 扫描或替换历史 cohort。

### 14.3 Audit 报告

- 保存原始结构化输出、规范化结果、证据引用和 Schema/生成来源。
- 页面显示摘要、维度覆盖、问题优先级、具体证据、缺口及相关 Plan/Task。
- N/A、未检查、失败与零分分开；覆盖不足不得显示成完整评估。
- 原始 JSON 可在技术详情查看，不能把整段校验错误铺满 AM 页面。
- 手动 Audit 与已启用周期 Audit 共用管道并去重，保留独立运行/结果。
- Audit 建议转成 Plan/Task 时保留来源；不能因发现问题直接公开修改。

### 14.4 看板与指标最低覆盖

| 领域 | 需要显示的内容 |
| --- | --- |
| GBP | 总/地图/搜索曝光、网站/电话/路线等行动、逐日趋势、覆盖门店与缺失 |
| GSC | 点击、曝光、CTR、平均位置、query/page 维度、property 范围和数据日期 |
| 评价 | 数量、评分、回复覆盖、未处理事项、趋势和主题；未知不能显示 0 |
| 关键词 | 来源、评分/评分顺序、批准监测集、目标页面、实际搜索词区分 |
| Local Falcon | ARP、ATRP、SoLV、Top 3 覆盖、网格、参数、报告日期、缺测和比较资格 |
| 执行 | 本期承诺、草稿/审核/已发布/已验证数量、延期、阻塞与后续工作 |
| 数据质量 | 来源、最后成功同步、数据截至日、覆盖率、失败/迟到/不可比说明 |

指标公式由有版本的确定性注册表定义。ARP/ATRP/SoLV 不能由 LLM 临时解释计算；网格、半径、中心点、关键词 cohort、语言/设备、排名截断规则改变后须明确不可比或建立新基线。

## 15. 周/月/自定义周期报告与导出

### 15.1 三种产品对象分开

- 实时看板：最新有效观测，可持续更新。
- 分析：对一组输入作解释和建议，保留证据强度。
- 冻结报告：固定范围、时间、来源、数据和叙事；查看时不重新算实时值。

### 15.2 生成链

~~~text
已启用周期 / AM 请求
    → 创建报告 Task
    → 解析范围与比较期间
    → 冻结 Snapshot + 数据质量检查
    → 程序计算指标与图表数据
    → 报告 Agent 生成有来源的叙事和版式计划
    → 确定性校验与渲染
    → AM 审核
    → 可交付网页 / PDF / 可编辑 PPTX
    → 明确的客户交付动作与记录
~~~

周、月、自定义期间使用门店/数据源明确的时区与日期基准；比较期必须可见。不静默把多商户重复 property 累加。迟到数据可生成修订报告，不能改变已经交付的文件。

### 15.3 ReportSnapshot / ReportEdition

建议保存：

- scope manifest、主/比较期间、timezone/date basis。
- source batch IDs、keyword cohort、formula/schema revision。
- 完整规范化渲染 payload、来源引用和内容 hash。
- 数据质量结果、叙事结论与对应证据。
- Agent/模型/Skill 运行引用、renderer/template revision。
- HTML/PDF/PPTX 各自 artifact hash、生成与验证状态。
- AM 审阅、修订原因、被替代版本、客户交付记录。

重新生成 AI 文字不保证字节相同；复现应读取已存叙事和 payload。文件可下载验收以归档文件 hash 为准；重复渲染至少保证语义、数值和版式一致，若要求字节一致须规范化时间戳等元数据并单独测试，不能泛称“所有 PDF/PPTX 天然字节复现”。

### 15.4 面向老板的结构

1. 本期结论与数据可信度。
2. 目标完成、主要成果和未完成原因。
3. GBP/GSC/评价表现与明确比较。
4. 关键词评分/监测、排名与点阵图。
5. 本期具体执行、证据和交付链接。
6. 风险、数据缺口、需要老板决定的事项。
7. 下周期建议与所需资源。

PDF 适合阅读与归档；PPTX 保留可编辑文本、表格和主要图表，不接受把整页截图塞进 PPT 冒充可编辑。两者都通过中文字体、分页/溢出、图例、表格、数字、来源与内容完整性检查。

用户提供的旧 HTML 和 Momotaro PDF 是最低信息覆盖参考，不以本节摘要代替逐页核对。报告子项目开始前建立“原报告信息项 → 新看板/报告位置 → 来源 → 验证方式”的覆盖清单；本次总架构不声称已完成原 PDF 全量复刻验收。

### 15.5 交付边界

- Agent 可以自动生成草稿，不等于自动发送。
- 数据不完整可以形成明确标注的内部草稿；身份/完整性红色问题不能生成“有效正式报告”。
- 客户交付需要已批准 edition 和明确接收范围。
- 签名 URL 到期不代表报告丢失；服务端保管稳定 artifact 引用并按权限签发访问。
- 外部发送结果未知先对账，不能重复发送多份。
- 未具备发送连接器时提供下载和人工交付记录，不声称已送达。

## 16. 技术架构与系统边界

~~~text
AM Web 工作台 / 商户 / 任务 / 报告
                 │
         SEO Ops 应用 API
                 │
 ┌───────────────┼──────────────────┐
 │               │                  │
业务状态服务   权限与政策校验      Snapshot / Memory Adapter / Catalog
 │               │                  │
 └───────────────┼──────────────────┘
         事件记录 + outbox
                 │
       scheduler / durable workers
                 │
        Core AI Adapter / 来源适配器
                 │
     Core AI Agent + 原生 Memory + 受控工具/数据提供方
                 │
     成果存储 → 验证 → 事件反馈
~~~

### 16.1 模块边界

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| 业务服务 | 商户、Plan、Task、依赖、状态与事务 | 模型自由写状态 |
| Policy Service | 身份、授权、预算、审批校验 | SEO 内容质量推理 |
| Orchestration Service | 构建上下文、调用决策 Agent、验证/应用命令 | 直接替 AM 审批 |
| Execution Service | 派发、lease、尝试、对账、恢复 | 以 API 200 代替交付 |
| Memory Adapter / 治理 | 复用原生记忆、核验隔离、提供已确认上下文、治理规则提升 | 重建原生经验引擎或另存可变业务真相 |
| Capability Catalog | Agent/Skill/模型绑定、核验与漂移 | 未经批准发布远端配置 |
| Data/Report Service | 固定数据口径、冻结、渲染、导出 | 无证据因果结论 |
| Core AI Adapter | 协议、配置能力预检、运行与结果获取 | 外部平台代码改造 |

### 16.2 安全与数据治理

- 每次读取、检索、派单、下载都校验商户/资产权限，不只在 UI 隐藏。
- 网页、评价、外部报告、模型输出视为不可信数据，不能作为系统指令。
- 工具列表最小化；写工具不能暴露给仅负责准备内容的角色。
- 对外部 URL 获取和报告渲染设置网络限制，防止 SSRF；HTML 需安全处理和隔离，不能执行用户文件脚本作为业务操作。
- 日志脱敏，Secret 只在服务端使用；模型调用仅发送必要数据。
- 人工决定绑定真实登录会话；对敏感操作记录身份和批准对象。
- 每次发布前检查最近权限撤销，后台开关可以停止新增写入。
- 备份与恢复覆盖业务数据库、Artifact、配置及索引重建流程；恢复演练证明批准证据和外部对账记录未丢失。


### 17.3 API 职责面

- Plan：草拟、提交审批、批准/拒绝、暂停、变更提案。
- Task：创建提案、分派/接手/转交、提交成果、记录 blocker、请求核验。
- Approval：审阅内容、批准/拒绝/撤销。
- Orchestration：决策记录、已应用命令、拒绝原因与 shadow replay。
- Memory：原生记忆只读观察/能力核验、Ops 规则候选与确认、来源/使用记录；远端删除或配置另走授权。
- Report：创建、质量检查、审阅、导出、修订、交付记录。
- Catalog：能力列表、绑定核验、漂移与模型政策。
- Events：按授权订阅真实状态变化；断连后按游标恢复。

所有写接口有身份、并发控制和幂等语义；命令接受不等于远端执行完成，返回 operation/task 引用而不是虚假的 done。

## 19. 最低成本验证与决策门槛

### 19.1 最大未知

真实事件下，动态 Orchestrator 是否比简单固定流程提供更有用的调整，同时不越权。第二个关联未知是记忆是否减少重复错误，而非制造错误泛化。

### 19.2 George 影子决策实验

不重做 UI、不发布 GBP、不发客户消息、不购买扫描、不创建真实执行任务。使用脱敏真实快照、一个明确的 Plan 授权包、真实 Core AI 调用，输出只存实验结果。模型调用预算在实验启动前明确。

预先由人定义允许动作、禁止动作和可接受替代方案：

| 场景 | 最低正确行为 |
| --- | --- |
| 正常前置完成 | 推进获授权且已就绪的后续工作 |
| 缺少素材/价格 | 分派 AM 补充，仅阻塞依赖项 |
| AM 退回草稿 | 正确携带反馈，不重复创建同一工作 |
| 计划外需求/超预算 | 请求变更，不自行扩大范围 |
| 发布结果未知 | 请求核验，不重发公开写入 |
| 重复/乱序事件 | 不重复派单，不覆盖较新状态 |

与简单固定规则表比较。六场景是低成本筛查，不是统计充分的生产评测。

### 19.3 记忆与多模型对照

- 在隔离试验中比较无记忆、显式已确认反馈和 Core AI 原生经验的行为，分清三者收益；控制原生提取与注入，避免试验污染正式池。
- 使用相似变体和不应适用的反例，检查迁移与边界。
- 比较高能力规划 + 经济执行、全高能力基线，以及必要时升级。
- 固定事实、权限、验收和上下文；记录模型实际身份、调用成本与人工修正。
- 不把评测标准或期望答案写进被评测 Agent 的隐藏提示。
- 模型非确定性存在；进入真实自动化前需要不同事件顺序/措辞的重复与留出测试。

### 19.4 分支决定

| 结果 | 下一步 |
| --- | --- |
| 有用调整明显且安全门通过 | 做范围受控的动态编排闭环 |
| 大部分决策等同简单规则 | 常规调度固定化，Agent 聚焦分析/内容/异常建议 |
| 越权、重复或依赖大量补充上下文 | 保持建议模式，先补事实、权限和输入契约 |
| 记忆减少重复错误且无跨范围泛化 | 启用可审阅商户记忆 |
| 记忆造成误用或事实冲突 | 暂停自动提升，只保留显式确认与检索 |
| 经济模型合格总成本更低 | 该任务类型采用经济模型与有限升级 |
| 经济模型返工抵消节省 | 保留高能力模型或缩小经济模型职责 |

任何安全硬门失败都不能用“平均准确率高”抵消。最终生产通过阈值按任务风险与留出测试确定，不从六个案例外推“已可靠”。

## 21. 验收清单与设计自检

### 21.1 必须通过的硬门

- [ ] Plan 未批准/暂停/过期/超范围时，不派发对应工作。

## 附录 A：George 完整示例

以下是流程示例，不代表 George 当前实际活动、价格或授权。

1. AM 提出“下周推广早餐，不增加预算，内容先给我审核”。
2. 系统读取 George 的服务范围、门店绑定和已确认事实；生成候选 Plan。
3. AM 批准目标、范围、交付与资源限制。
4. Orchestrator 发现价格未确认，创建 AM 资料任务；同时让内容 Agent 准备不依赖价格的部分。
5. AM 提交老板确认依据，事实服务产生已确认记录。
6. 内容 Agent 使用经济模型和相关品牌记忆生成草稿，程序做结构/事实引用检查。
7. 若多次不合格且政策允许，升级模型；缺少素材则返回明确 blocker。
8. AM 审核具体文案、图片、CTA 和目标门店；退回意见关联原稿。
9. 生成新稿后旧批准不沿用；批准新稿产生绑定 hash 的授权记录。
10. 执行者发布；若结果未知，先对账；确认外部结果满足条件后完成。
11. Orchestrator 接收完成事件，更新 Plan 交付进度，不因重复事件再发一条 Post。
12. 报告 Agent 使用冻结数据和实际交付记录准备周报；不声称一条 Post 导致所有排名提升。
13. AM 审核报告并明确交付；文件与交付记录归档。
14. 本次退回理由提炼为候选记忆，经确认后供下次使用；不自动授予未来发布权。
15. 下一周期新 Plan 基于结果和有效记忆提出，超出旧周期授权的工作重新审批。

## 附录 B：术语

- Agent：有明确职责、输入输出和能力边界的执行/判断单元；不等于模型名称。
- AM：人类 Account Manager，商户服务负责人，也是任务参与者。
- Orchestrator：在授权范围内规划和协调工作的 Agent。
- Skill：可复用的执行知识、流程和工具使用规范，不自动携带业务授权。
- Plan：目标、交付安排和有限自主权限的载体。
- Task：可以独立交付、交接或验收的工作。
- Execution：一次实际尝试；Task 可以有多次。
- Run：Core AI 提供的真实运行对象，存在时关联。
- Artifact：需要查看、审核、交付或验证的成果。
- Snapshot：固定范围、时间与来源的数据/输入集合。
- Memory：有来源、范围和时效的可检索事实/决定/经验。
- Policy：程序可以检查的权限、预算、路由和升级规则。
- Shadow：真实输入下只提出建议，不应用到业务执行的验证模式。
