# 新商户初诊与 Plan 确认设计

日期：2026-09-01
状态：已与 Xander 逐段确认，进入第一版实现

## 目标

新商户进入 SEO Ops 后，先基于公开信息和已提供资料完成一次本地 SEO 初诊，再由 Planner Agent 形成带日期的任务 Plan。运营人员只确认 Plan；确认后具体任务进入可执行队列。涉及 GBP、官网等外部写入的任务，仍需在执行前单独审批。

## 系统边界

- 所有产品前端、后端、持久化、审批和调度代码只进入 `connexup-seo-ops`。
- Core AI Server 是外部 Agent 能力提供者，通过现有服务端适配器调用；不修改 Core AI 代码。
- FBR Project 是只读数据来源；不修改其代码。
- SEO Ops 数据库是商户、诊断 Run、Plan 确认和任务状态的唯一业务真相。

## 第一版范围

1. 新建商户补充 `primary_location` 与 `website_url`，用于公开诊断。
2. 前端创建商户后立即请求现有分析 Run；Core AI 未配置或触发失败时保留商户，并在商户页提供重试。
3. 初诊 Prompt 明确要求：美国本地商户、英文关键词、证据化问题清单，以及可解析的带日期 Plan JSON。
4. 初诊完成后沿用现有 `plan_parser` 创建候选任务，但候选任务在 Plan 确认前不能从 `todo` 进入 `doing`。
5. 分析 Run 增加 `plan_approved_at`；成功且已生成任务的 Run 才能确认 Plan，确认操作幂等。
6. 商户页只展示一个紧凑的初诊状态卡：未开始、诊断中、失败、待确认 Plan、Plan 已确认。
7. 分析报告页正文保持主内容，右侧任务清单提供唯一的“确认 Plan”动作。

## 用户流程

```text
新建商户
  → 保存名称、地点、网站
  → 自动发起公开初诊
  → Agent 返回诊断报告和 Plan JSON
  → SEO Ops 生成候选任务
  → 运营人员查看报告并确认 Plan
  → 候选任务进入可执行状态
```

如果自动初诊没有启动，商户仍创建成功；商户页显示原因和“重新开始诊断”。如果诊断成功但没有产生候选任务，不能确认空 Plan，页面提示重新分析或检查报告。

## 状态与约束

- `runs.status` 继续使用 `running / succeeded / failed`。
- `runs.plan_approved_at` 为空表示 Plan 草案未确认；有值表示已确认。
- 历史成功 Run 在迁移时以 `finished_at` 回填为已确认，避免阻塞现有任务。
- 人工创建任务没有 `source_run_id`，不受 Plan Gate 影响。
- 来自分析 Run 的任务只有对应 Run 已确认后才能开始；完成、取消等既有规则不变。
- 批量开始与单任务开始使用同一 Gate，不能通过批量接口绕过。

## UI 方向

- PC 内部运营台，继续使用左侧导航与浅色工作台。
- 新建商户改成按钮展开的三字段录入区，避免表头长期堆放输入框。
- 商户工作区不增加复杂流程图，只用一句状态、一个下一步动作和必要错误说明。
- 分析报告页的 Plan 确认位于生成任务列表上方；技术 Run ID 与内部校验默认不突出。
- 文案从运营人员视角描述动作，例如“查看并确认 Plan”“重新开始诊断”，不暴露编排术语。

## 暂不包含

- 完整问卷系统、文件附件和第三方授权向导。
- 多 Agent 并行诊断拆分与独立进度条。
- GBP/官网发布审批与回读证据的数据模型。
- 新的 Core AI Agent 或 Skill 创建。
- FBR Project 写入或代码修改。

这些能力在本闭环投入使用后，按独立规格继续增加。
